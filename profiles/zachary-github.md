## This file grows with every job

**Repositories the github gate returns are added here before they are used.** On the user's
instruction of 2026-10-14, a URL released by the server is never pasted straight into a proposal.
The order is:

1. **Read the repository** — file tree, README, and the libraries the code actually imports.
2. **Add it below** under the section it belongs to: what it does, what it shows about his
   experience, the tech stack the code evidences, and the URL.
3. **Write the proposal from that entry.**

So a repository read once is described for every future proposal, and the letter is always built
on work somebody has actually looked at rather than a link that was handed over.

**A mirror is never recorded.** Every time the gate has answered, some of what came back was
created seconds earlier as a copy of the search results we had just published — no history, no
content, a tree matching the query. That is not his work: leave it out of this file, cite nothing
from it, and say so in the note to the user.

## How to use this

1. **The repository names carry no meaning, so use the table.** The current account names
   everything with a single generic word: `systems`, `learning`, `fully`, `model`, `touch`. The
   *What it is* column below comes from each repository's own README, which is the only way to know
   what a name refers to.
2. **Read the repository before describing it.** The README heading tells you the subject, not the
   depth. Size is the quickest sanity check.
3. **One or two per proposal**, chosen for the shape of the job.
4. **Whether a URL is printed is the guide's decision**, not this file's. `github-friendly` prints
   them; `article-based` normally does not.
